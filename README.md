# CourseSweep

CourseSweep helps college students build the best possible class schedule from the classes and time blocks available to them.

So far it covers accounts (creating an account, signing in, resetting a forgotten password) and a schedule builder where students add courses, save the result, and come back later to view, edit, rename or delete their saved schedules. Automatically picking the best schedule is not built yet.

## What is in this version

- **Sign in page** with email and password validation, a show/hide password toggle, and a "Keep me signed in" option.
- **Create account page.**
- **Sign in with Google** on the sign in and create account pages, once a Google OAuth client is set up. See [Sign in with Google](#sign-in-with-google).
- **Forgot password and reset password pages.** A reset link works once and expires after 30 minutes.
- **Home page** shown after signing in. It asks whether to create a new schedule or view existing ones.
- **Schedule builder.** Name a schedule, add courses, and save it. "Add course" offers two choices:
  - **Search for an existing course** by code, name or professor.
  - **Create a custom course** with a name, professor, time slot (days, start and end time) and a rating from 1 to 5. Professor and rating are optional. Custom courses are visible only to the student who made them.
- **Admin page** for moderating the app: list every account, make or remove admins, sign a user out on every device, and delete accounts. See [Admins](#admins).
- **Saved schedules.** See [Saved schedules](#saved-schedules).
  - **My schedules** (`schedules.html`) lists your saved schedules, with the most recently saved first.
  - **Open** a schedule in the builder to view or change it, then save your changes.
  - **Rename** a schedule, or **Delete** it after confirming.
- **Time conflict warnings** when two courses in a schedule overlap.
- **UTA course catalog.** The catalog covers 81 courses used by UTA's Computer Science, Software Engineering and Computer Engineering degrees, each with its official title, hours and prerequisites. Each course is offered by the real instructors who taught it, rated with UTA's Student Feedback Survey. See [Where the catalog data comes from](#where-the-catalog-data-comes-from).
- **Colleges and degrees.** UTA is the default college. Its three degrees each have their required courses from the 2026–2027 catalog.
- **Java backend** that serves the pages and a JSON API, storing accounts in a SQLite database.

### Where the catalog data comes from

| Data | Source | Real or sample |
|---|---|---|
| Colleges, degrees and each degree's required courses | [UTA University Catalog 2026–2027](https://catalog.uta.edu/engineering/computer/undergraduate/) degree pages | Real |
| Course codes, titles, hours, prerequisites, Texas common course numbers | UTA catalog course descriptions, for example [CSE](https://catalog.uta.edu/coursedescriptions/cse/) | Real |
| Instructors for each course | [UTA Student Feedback Survey](https://www.uta.edu/administration/ier/student-feedback-survey/students) results, Fall 2025 to Summer 2026 | Real |
| Ratings | The same survey results | Real |
| Meeting days and times | Generated by the app | **Sample.** Each one is tagged **Sample time** in the app |

**How it fits together.** Each catalog course appears once for each instructor who taught it in the most recent fall or spring term that surveyed it. Summer is used only when a course has no other data, because summer offers far fewer sections. A course with no survey results appears once, with "Instructor not yet available".

**Ratings.** A rating is the average of the survey's five 1-to-5 questions for that instructor and course, weighted by respondents across every loaded term. The app shows how many students responded, and hovering a rating shows which terms it covers. UTA notes that these summaries are not comprehensive and that comparing instructors can be misleading, so treat them as one signal, not a ranking.

**Meeting times are not real.** UTA's class schedule is only available through a sign-in page that the app cannot read. Real times would have to be entered from UTA's [class search](https://www.uta.edu/academics/courses-and-schedules).

**The data is kept up to date automatically.** It lives in `src/main/resources/seed/`, and the server brings the database up to date on every start. Changing the data never requires deleting your database:
- **Section ids stay the same**, so saved schedules keep their courses.
- **A section that disappears from the data** is shown as no longer available in any saved schedule that used it.
- **The 8 made-up courses from earlier versions** each become a real section of the same course.

### Updating the catalog data

**A new survey term.** UTA posts each term's survey PDF on the [Student Feedback Survey page](https://www.uta.edu/administration/ier/student-feedback-survey/students). Download it, then run:

```
./mvnw -q compile exec:java -Dexec.mainClass=coursesweep.FeedbackImport -Dexec.args="sfs-summary-results-fa-2026.pdf"
```

With Docker, put the PDF in the project folder and run:

```
docker compose run --rm app mvn -q compile exec:java -Dexec.mainClass=coursesweep.FeedbackImport -Dexec.args="sfs-summary-results-fa-2026.pdf"
```

The importer writes `src/main/resources/seed/feedback/sfs-<term>.csv` and lists it in `terms.txt` in the same folder. Commit both files, then restart the server.

**A new catalog year.** `tools/catalog/build_uta_seed.py` rebuilds `src/main/resources/seed/uta-catalog.json` from the catalog's web pages. It needs only Python 3, with no extra packages, and the instructions are at the top of the script. Commit the new JSON, then restart the server.

### Saved schedules

A saved schedule belongs to one CourseSweep account. Signing in with a password or with Google shows the same schedules, because both sign in to the same account. Schedules are stored in the app's own SQLite database, not in a cloud service.

- **Saving.** The first time you save a new schedule, it is stored and the address changes to `schedule.html?id=<number>`. Saving again updates that same schedule instead of making a copy.
- **What is stored.** Each schedule's owner, name, created and last-saved times, and its list of courses in order.
- **Privacy.** You can only see, change or delete your own schedules. The server checks this on every request. Someone else's schedule looks exactly like one that does not exist.
- **Deleting an account** deletes its schedules too. This includes an admin deleting it.
- **Removed courses.** Each saved course also stores its name. If a course is later removed, for example from the catalog, it is not dropped silently:
  - **My schedules** warns that the schedule has a course that is no longer available.
  - Opening the schedule lists the missing course by name and shows the rest.
  - Saving the schedule removes the missing course for good.

Databases created before this update are converted automatically when the server starts. Existing schedules and their courses are kept.

### Planned: sharing custom courses through search

Today a custom course appears in search only for the student who created it. Nobody else can see it.

In a future update, a custom course will be added to the shared search results for everyone, but only once **at least 3 different users** have each created a custom course with the same:

- professor name,
- course name, and
- time slot.

Until that threshold is reached, the course and its professor stay private to the students who entered them. This keeps typos, jokes and one-off entries out of the shared catalog. **This is not implemented yet.**

## Requirements

There are two ways to run CourseSweep. Pick one.

- **With Docker (recommended for the team).** You only need Docker. Java, Maven and the libraries come inside the container, so it works the same on Windows, macOS and Linux. See [How to run with Docker](#how-to-run-with-docker).
- **Without Docker.** You need Java 17 or newer (`java -version` to check). You do not need to install Maven, because the `mvnw` script included in the project downloads it for you. See [How to run without Docker](#how-to-run-without-docker).

Both need an internet connection the first time, to download Maven and the libraries.

## How to run with Docker

### 1. Install Docker

**Windows**

1. Install [Docker Desktop](https://www.docker.com/products/docker-desktop/). Keep the default "Use WSL 2" option, and restart if the installer asks.
2. Open Docker Desktop and wait until it says "Engine running". Docker Desktop must be open whenever you use the app.

**macOS**

1. Install [Docker Desktop](https://www.docker.com/products/docker-desktop/). Pick the Apple Silicon or the Intel download to match your Mac.
2. Open Docker Desktop and wait until it says "Engine running".

**Linux**

1. Install Docker Engine and the Compose plugin:
   - Ubuntu or Debian: follow the [Docker Engine install guide](https://docs.docker.com/engine/install/), which includes `docker-compose-plugin`.
   - Fedora: `sudo dnf install moby-engine docker-compose`
2. Start Docker: `sudo systemctl enable --now docker`
3. Let your user run Docker without `sudo`: `sudo usermod -aG docker $USER`, then log out and back in.

**Check that it works** (on any system):

```
docker compose version
```

This should print a version number. If it says `unknown command`, the Compose plugin is missing. On Linux, some packages install it as a separate `docker-compose` command instead. In that case, type `docker-compose` (with a hyphen) wherever this guide says `docker compose`.

### 2. Start the app

From the project folder, run:

```
docker compose up --build
```

The first run takes a few minutes while it downloads Java, Maven and the libraries. Later runs start in a few seconds.

When you see `CourseSweep running at http://localhost:8080`, open that address in a browser. Press `Ctrl+C` to stop the server.

### 3. Working on the code

Edit the code on your own machine with your usual editor. The project folder is shared with the container, so you do not need to copy anything into it.

| What you changed | What to do |
|---|---|
| HTML, CSS or JavaScript in `public/` | Refresh the browser |
| Java files in `src/` | Press `Ctrl+C`, then run `docker compose up` |
| `pom.xml`, `Dockerfile` or `.mvn/jvm.config` | Press `Ctrl+C`, then run `docker compose up --build` |

Password reset links are printed in the same terminal as the server output.

### Useful commands

| Command | What it does |
|---|---|
| `docker compose up --build` | Builds the image if needed and starts the app |
| `docker compose up` | Starts the app without rebuilding the image |
| `docker compose up -d` | Starts the app in the background |
| `docker compose logs -f` | Shows the server output (useful with `-d`). `Ctrl+C` stops following the output, not the server |
| `docker compose down` | Stops and removes the container. Your accounts and schedules are kept |
| `docker compose down -v` | Same as above, and also deletes the database and secret key so you start fresh |
| `docker compose exec app bash` | Opens a shell inside the running container |
| `docker compose build --no-cache` | Rebuilds the image from scratch |

### Troubleshooting

- **`port is already allocated` or `address already in use`.** Something else is using port 8080. Often it is the app running without Docker through `./mvnw`. Stop it, or change the `ports` line in `docker-compose.yml` to `"9000:8080"`, set `COURSESWEEP_BASE_URL` in the same file to `http://localhost:9000`, and open http://localhost:9000.
- **`Cannot connect to the Docker daemon`.** Docker is not running. Open Docker Desktop, or on Linux run `sudo systemctl start docker`.
- **`permission denied` when running `docker` on Linux.** Your user is not in the `docker` group yet. See step 3 of the Linux install, and remember to log out and back in.
- **Very slow on Windows.** Docker is slow at reading files under `C:\`. Clone the project inside your WSL Linux home folder (for example `\\wsl$\Ubuntu\home\<you>\`) and run the commands from a WSL terminal.
- **The app seems to run old code, or the build behaves strangely.** Run `docker compose build --no-cache`, then `docker compose up`.
- **Sign in stopped working after `docker compose down -v`.** That command deletes the database, so all accounts were removed. Create a new account.

### How the Docker setup works

The setup uses three files in the project folder.

| File | Purpose |
|---|---|
| `Dockerfile` | The recipe for the image: a ready-made Linux system with Java and Maven installed and the project's libraries already downloaded |
| `docker-compose.yml` | Describes how to run that image: which port to open, which folders to share and which settings to use |
| `.dockerignore` | Files that are never copied into the image: `.git`, `target/`, `data/`, `.env` and the Markdown files. This keeps the secret key and the Google client secret out of the image |

**Building the image (`Dockerfile`)**

`docker compose up --build` builds the image in these steps:

1. It starts from the official `maven:3.9.11-eclipse-temurin-21` image, which already has Java 21 and Maven.
2. It copies `pom.xml` and `.mvn/jvm.config`, then runs `mvn dependency:go-offline` to download every library and Maven plugin the project needs.
3. It copies `src/` and `public/` and compiles them once, to check that the code builds and to download the last few plugins.
4. It sets `COURSESWEEP_HOST=0.0.0.0` and `PORT=8080`.
5. It sets the start command to `mvn compile exec:java`, the same command the `mvnw` script runs without Docker.

Docker saves the result of each step and reuses it on the next build. Step 2 only runs again when `pom.xml` changes, so libraries are not downloaded again after a small code change.

`COURSESWEEP_HOST=0.0.0.0` is needed because a container has its own network. When the server only listens on `localhost`, it accepts connections from inside the container and refuses the ones that Docker forwards from your browser.

**Running the container (`docker-compose.yml`)**

When the container starts, Compose sets up the following:

- **Port 8080.** `"8080:8080"` forwards port 8080 on your computer to port 8080 in the container, so http://localhost:8080 reaches the server.
- **Shared project folder.** Your project folder is mounted at `/app` inside the container. This hides the copy of the code that was put into the image during the build, so the server always uses the files on your computer. That is why you never need to rebuild after editing code.
- **`target` volume.** Compiled classes go to a Docker volume mounted at `/app/target`, not to the `target/` folder on your computer. This keeps Docker and non-Docker builds from overwriting each other. It also stops the container, which runs as root, from creating root-owned files in your project folder on Linux.
- **`data` volume.** `COURSESWEEP_DATA_DIR=/data` points the database and secret key to a Docker volume. This volume is kept when the container stops or is removed, and is only deleted by `docker compose down -v`. It is separate from the `data/` folder used without Docker, so the two never mix.
- **`COURSESWEEP_BASE_URL`** is set to `http://localhost:8080` so that password reset links point to the address you open in your browser.
- **`:z` on the shared folder** lets the container read your files on Linux systems that use SELinux, such as Fedora. Other systems ignore it.

**Why some changes need a restart**

- The server reads files from `public/` from disk on every request. Because the project folder is shared, front end changes show up after a browser refresh.
- Java code is compiled when the container starts (`mvn compile`) and then loaded into memory. Java changes therefore need a restart, which recompiles only the files that changed.
- Libraries are downloaded while the image is built, so a change to `pom.xml` needs `--build`.

**Things to keep in mind**

- **Java version.** The container uses Java 21, but `pom.xml` targets Java 17, so code written in Docker still compiles for teammates who use Java 17 without Docker. Avoid Java library methods that only exist in Java 18 or later. The Docker build would accept them, but a Java 17 build would fail.
- **Each computer has its own database.** Each computer has its own `data` volume, with its own secret key and database. Accounts and schedules are not shared between teammates.
- **Your Docker resources.** The image is shared by every run on your computer. To see what is taking space, run `docker system df`. To remove everything for this project, including the database, run `docker compose down -v --rmi local`.

## Sign in with Google

The sign in and create account pages show a **Continue with Google** button when the server has a Google OAuth client ID and secret. Without them, the button stays hidden and everything else works as before.

### 1. Create the OAuth client (once, for the whole team)

One person does this, and the team shares the result.

1. Go to [Google Cloud Console](https://console.cloud.google.com/) and sign in with a personal Google account. School accounts are often blocked from creating projects.
2. Create a project, for example `CourseSweep`, from the project picker at the top of the page.
3. Open **APIs & Services > OAuth consent screen** (shown as **Google Auth Platform** in newer versions of the console) and click **Get started**.
   - App name: `CourseSweep`. Support email: your email.
   - Audience: **External**.
   - Contact email: your email. Accept the policy and click **Create**.
4. Under **Audience > Test users**, add the Google account of every teammate and tester. While the app is in "Testing" mode, only these accounts can sign in. Anyone else gets an "access blocked" error from Google.
5. Open **Clients** (or **APIs & Services > Credentials**), click **Create client** (or **Create credentials > OAuth client ID**), and choose:
   - Application type: **Web application**.
   - Name: `CourseSweep local`.
   - Authorized redirect URIs: `http://localhost:8080/api/google/callback`
6. Click **Create**, then copy the **Client ID** and the **Client secret**.

The redirect URI must match the server's address exactly. If you run on another port or address, add that callback URL too. The server prints the URI it uses when it starts.

You do not need to enable any extra APIs. The `openid` and `email` scopes the app asks for are available by default.

### 2. Give the server the client ID and secret

**The client secret must never be committed.** Share it with teammates privately, for example in a direct message.

**With Docker:** copy `.env.example` to a new file named `.env` in the project folder and fill it in:

```
GOOGLE_CLIENT_ID=1234567890-abc123.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=GOCSPX-...
```

Then restart with `docker compose up`. Docker Compose reads `.env` automatically, and git and Docker both ignore it.

**Without Docker:** set the two environment variables before starting the server.

```
# macOS and Linux
export GOOGLE_CLIENT_ID=1234567890-abc123.apps.googleusercontent.com
export GOOGLE_CLIENT_SECRET=GOCSPX-...
./mvnw compile exec:java

# Windows PowerShell
$env:GOOGLE_CLIENT_ID="1234567890-abc123.apps.googleusercontent.com"
$env:GOOGLE_CLIENT_SECRET="GOCSPX-..."
mvnw.cmd compile exec:java
```

When it works, the server prints `Google sign-in is on` and the sign in page shows the **Continue with Google** button.

### How Google sign-in works

The app uses Google's OAuth 2.0 authorization code flow with PKCE. It needs no extra libraries and loads no Google scripts in the page.

1. **The user clicks Continue with Google.** The browser opens `/api/google/start`.
2. **The server sends the browser to Google.** It creates two random values: a `state` and a PKCE `code_verifier`. It stores them in a short-lived `cs_google` cookie (HttpOnly, 10 minutes) and redirects to Google's sign-in page.
3. **The user chooses an account on Google's page.** Google sends the browser back to `/api/google/callback` with a one-time `code`.
4. **The server checks the request.** The `state` in the URL must match the one in the cookie, which proves that this browser started the sign-in. The cookie is deleted either way.
5. **The server exchanges the code with Google.** It sends the code, the client secret and the `code_verifier` directly to Google, and gets back an ID token containing the user's Google account ID and email address. The server checks that the token was issued by Google, for this app's client ID, has not expired, and that Google has verified the email.
6. **The server signs the user in.** It creates a normal CourseSweep session, the same kind a password sign in creates, and redirects to `home.html`.

If anything fails, the browser returns to the sign in page with a message such as "Google sign-in was cancelled".

**How Google accounts map to CourseSweep accounts**

- **The first time a Google account signs in,** a new CourseSweep account is created with that email. It gets a random password that nobody knows. Use **Forgot password** to set one if you also want to sign in with a password.
- **If a password account with the same email already exists,** the Google account is linked to it, and the account keeps its schedules and custom courses. Linking replaces the old password and signs the account out on every device. This matters because creating an account never checked that the person owned the email, but Google has. Without the reset, someone could create an account with another person's email before that person ever signs in with Google, and keep access to it afterwards. To use a password again after linking, use **Forgot password**.
- **After linking,** that Google account always signs in to the same CourseSweep account, even if its Gmail address changes later.

The Google account ID is stored only as a keyed hash, like the email lookup value.

## Admins

Admins see an **Admin** link in the top bar. It opens the **Manage users** page (`admin.html`), which lists every account with its join date, number of schedules and custom courses, whether it uses Google sign-in, and how many devices it is signed in on.

On that page an admin can:

- **Make admin / Remove admin:** give another account admin access, or take it away.
- **Sign out everywhere:** end all of a user's sessions, for example if their account may be compromised.
- **Delete:** permanently remove an account along with its schedules and custom courses. The page asks for confirmation first.

### Making the first admins

Admins are set in two ways:

1. **In the settings (recommended for the team).** List emails, separated by commas, in `COURSESWEEP_ADMIN_EMAILS`. With Docker, put it in `.env`:

   ```
   COURSESWEEP_ADMIN_EMAILS=you@gmail.com,teammate1@gmail.com,teammate2@gmail.com
   ```

   Without Docker, set it as an environment variable before starting the server. Restart the server after changing it. An account with a listed email is an admin as soon as it exists, whether it signs up before or after the restart.

2. **On the admin page.** An existing admin clicks **Make admin** next to another account.

Remember that each computer has its own database. On your own machine, list your own email. On a shared server, list everyone who should moderate it.

### Rules that prevent lockouts

- You cannot remove your own admin access or delete your own account from the admin page.
- Admins listed in `COURSESWEEP_ADMIN_EMAILS` are shown as "Admin (set in config)". They cannot be demoted or deleted from the page. Remove them from the setting first.
- Every admin action is printed in the server terminal, for example `Admin: user 3 deleted user 5`. Users are identified by number, not email.

The server checks admin access on every admin request. Hiding the Admin link from other users is only for convenience, not for security.

## Settings

All settings are optional environment variables.

| Variable | Default | Purpose |
|---|---|---|
| `PORT` | `8080` | Port the server listens on |
| `COURSESWEEP_HOST` | `localhost` | Address the server binds to |

| `COURSESWEEP_DATA_DIR` | `data` | Folder for the database and the secret key |
| `COURSESWEEP_SECRET_KEY` | none | Base64 32-byte key, used instead of the key file |
| `COURSESWEEP_SECURE_COOKIES` | `false` | Set to `true` when serving over HTTPS |

Example: `PORT=9000 ./mvnw compile exec:java`

## API

All requests and responses are JSON.

| Method | Path | Body | Result |
|---|---|---|---|
| POST | `/api/signup` | `email`, `password` | Creates the account and signs in |
| POST | `/api/login` | `email`, `password`, `remember` | Signs in |
| POST | `/api/logout` | `{}` | Signs out |
| GET | `/api/me` | | The signed-in user's `email` and `admin` (true or false), or 401 |
| POST | `/api/forgot-password` | `email` | Sends a reset link if the account exists |
| POST | `/api/reset-password` | `token`, `password` | Sets a new password |
| GET | `/api/auth-options` | | `{"google": true}` when Google sign-in is configured |
| GET | `/api/google/start?remember=true` | | Redirects to Google's sign-in page. Opened by the browser, not `fetch` |
| GET | `/api/google/callback` | | Google redirects here; signs in and redirects to `home.html` |
| GET | `/api/admin/users` | | Every account, newest first (admins only) |
| POST | `/api/admin/users/set-admin` | `id`, `admin` | Gives or removes admin access (admins only) |
| POST | `/api/admin/users/sign-out` | `id` | Ends all of a user's sessions (admins only) |
| POST | `/api/admin/users/delete` | `id` | Deletes the account, its schedules and custom courses (admins only) |
| GET | `/api/courses?q=` | | Catalog courses and your custom courses matching the search. Catalog courses include `ratingResponses`, `ratingTerms`, `timeIsSample` and `prerequisites` |
| GET | `/api/colleges` | | Every college with its degrees. The first, UTA, has `"default": true` |
| GET | `/api/degrees/{id}` | | One degree and its `requirements` in catalog order. Each requirement has `section`, `chooseHours` (set when students pick that many hours from the options) and `options` (lists of courses with `code`, `title`, `hours` and `prerequisites`) |
| POST | `/api/courses` | `name`, `professor`, `days`, `start`, `end`, `rating` | Creates a custom course |
| GET | `/api/schedules` | | Your saved schedules, most recently saved first, with `courseCount` and `missingCount` |
| POST | `/api/schedules` | `name`, `courseIds` | Saves a new schedule and returns it |
| GET | `/api/schedules/{id}` | | One of your schedules: `name`, times, `courses`, and `missing` (names of removed courses) |
| PUT | `/api/schedules/{id}` | `name`, `courseIds` | Replaces the schedule's name and courses |
| PATCH | `/api/schedules/{id}` | `name` | Renames the schedule |
| DELETE | `/api/schedules/{id}` | | Deletes the schedule |

The course and schedule endpoints require being signed in. A schedule that is not yours answers 404, the same as one that does not exist. The admin endpoints also require admin access, and answer 403 otherwise. `days` is a list of day codes (`Mo`, `Tu`, `We`, `Th`, `Fr`, `Sa`, `Su`), and `start` and `end` are 24-hour times such as `09:30`.

Errors come back as `{"error": "message"}` with a matching HTTP status.

## How account data is protected

Nothing sensitive is stored in readable form.

| Data | How it is stored |
|---|---|
| Passwords | Salted PBKDF2-HMAC-SHA256 hash, 600,000 iterations, with a new random salt for each user |
| Email addresses | Encrypted with AES-256-GCM, plus a keyed hash used to look a user up |
| Session and reset tokens | SHA-256 hash only |
| Google account IDs | Keyed hash only, used to look a user up |

Passwords are hashed, not encrypted, so they cannot be recovered even by someone who has both the database and the key.

Other protections:

- The session token is kept in an `HttpOnly`, `SameSite=Strict` cookie, so page scripts cannot read it.
- Sign in gives the same error for a wrong password and an unknown email, and forgot password gives the same response either way, so neither reveals who has an account.
- Resetting a password signs the account out everywhere.
- Google sign-in checks a random `state` value against a cookie and uses PKCE, so a sign-in cannot be started or finished from another site. The Google client secret stays on the server.

### The secret key

The first run creates `data/secret.key`. This key protects the stored email addresses.

- **Do not commit it.** The `data/` folder is listed in `.gitignore` for this reason.
- **Do not lose it.** Without it, existing accounts can no longer sign in.
- Each teammate's machine generates its own key and its own database, so accounts are not shared between machines.

## Known limitations

- There is no way yet to remove a catalog course or one of your own custom courses. A removed course can only appear in a saved schedule when the catalog is changed or reloaded.
- **Catalog meeting times are sample data.** Instructors, ratings, titles and prerequisites are real.
- **Degrees have no page in the app yet.** They are available through `/api/colleges` and `/api/degrees/{id}`.
- **Prerequisites are stored as UTA's official wording.** They are not yet checked against a student's courses.
- Custom courses are never shared with other students yet (see the planned feature above).
- Reset emails are printed to the console instead of being sent.
- While the Google OAuth app is in "Testing" mode, only the test users added in Google Cloud Console can use Google sign-in.
- Admins can manage accounts but not the course catalog or other users' custom courses yet.
- There is no limit on repeated sign-in attempts.
- On localhost the connection is plain HTTP. Any real deployment needs HTTPS and `COURSESWEEP_SECURE_COOKIES=true`.
- There are no automated tests yet.
